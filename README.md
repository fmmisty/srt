# Step 2: 音声専用SRT送受信プロトタイプ 使い方

BUILD.md でlibsrtをインストール済みであることが前提です。

## ビルド

```bash
cd srt_audio
make
```

`libsrt.so` が `/usr/local/lib` にない場合は `sudo ldconfig` を再実行してください。

## 動作確認(まずはファイル→ファイルで疎通確認)

送信側 (Pi A):
```bash
cat test.raw | ./audio_srt_send 9000
```

受信側 (Pi B, Pi AのIPを指定):
```bash
./audio_srt_recv 192.168.1.10 9000 > received.raw
```

`test.raw` と `received.raw` を比較して欠落がないか確認(diff等)。

## リアルタイム音声(マイク→SRT→スピーカー)

送信側 (Pi A):
```bash
arecord -D hw:1,0 -f S16_LE -r 48000 -c 2 -t raw | ./audio_srt_send 9000
```

受信側 (Pi B):
```bash
./audio_srt_recv 192.168.1.10 9000 | aplay -f S16_LE -r 48000 -c 2 -t raw
```

- サンプルレート/チャンネル数はFM音声の要件に応じて調整してください(例: 32kHz/モノラルなら帯域をさらに絞れます)。
- `arecord -l` でオーディオデバイス一覧を確認し、`hw:X,Y` を実機に合わせて変更してください。

## パラメータ調整のポイント

| パラメータ | 説明 | 目安 |
|---|---|---|
| `latency_ms` (第2/第3引数) | ARQの再送猶予時間。無線区間のRTTより十分大きく設定 | 無線区間なら120〜250ms程度から調整 |
| `PAYLOAD_SIZE` (ソース内定数) | 1パケットあたりのペイロードサイズ | 1316byte(ライブモード推奨値)がデフォルト |

## 次のステップ(Step 3以降)

- 現状は**平文の生PCM**をそのまま流しているだけなので、実運用前には
  - 暗号化(`SRTO_PASSPHRASE` オプションを追加)
  - 音声コーデック圧縮(帯域を絞りたい場合、Opus等を挟む)
  - パケットロス/CCQ劣化を模擬した環境での耐性検証(`tc netem` でRTT/ロス率を人工的に付与するとテストしやすい)
- 実際のW56系のUDPパイプラインとの統合点の洗い出し

## Step 3: AACエンコード/デコード版(aac_srt_send / aac_srt_recv)

fdk-aac(AAC-LC)でPCMを圧縮してから送信する版。帯域を大幅に削減できる。
BUILD.mdの6でfdk-aacをビルド済みであることが前提。

```bash
make aac_srt_send aac_srt_recv
```

送信側 (Pi A, FMステレオ48kHz、96kbps):
```bash
arecord -D hw:1,0 -f S16_LE -r 48000 -c 2 -t raw \
  | ./aac_srt_send 9000 48000 2 96000 150
```

受信側 (Pi B):
```bash
./aac_srt_recv 192.168.1.10 9000 150 | aplay -f S16_LE -r 48000 -c 2 -t raw
```

引数:
- `aac_srt_send <port> [samplerate=48000] [channels=2] [bitrate=96000] [latency_ms=150]`
- `aac_srt_recv <host> <port> [latency_ms=150]`

動作確認済み(サンドボックス環境でのループバックテスト):
- 440Hz/660Hzのステレオテスト信号をPCM→AAC→SRT→AAC→PCMの全経路で転送し、
  デコード後のFFTピーク周波数が441Hz/661.5Hzと、誤差1Hz程度で一致することを確認済み。
- 帯域の目安: 96kbpsなら48kHz/16bit/stereoの生PCM(約1.4Mbps)から約1/14に圧縮。
  FM音声品質としては64〜96kbps(AAC-LC)あたりが実用的な下限の目安。

### 実運用に向けた追加検討事項
- 暗号化: `srt_setsockopt(sock, 0, SRTO_PASSPHRASE, ...)` を送受信双方に追加
- 長時間運用時の安定性(メモリリーク、再接続処理)は未検証。プロトタイプ段階の
  ため、本番投入前に長時間連続稼働試験が必要。

## パケットロス耐性検証(実施済み)

`udp_lossy_proxy.py`(tc netem 代替。sandboxでnetemカーネルモジュールが
使えない環境向けに自作したUDPロス/遅延注入プロキシ)を使い、
ロス率・遅延・ジッタ・latency_msの組み合わせで実際に送受信検証を実施した。

### メッセージ形式(v2: 種別タグ方式)

初期実装は「最初に受信したメッセージ=CONFIG(ASC)」という順序への決め打ちで
設計されていたが、パケットロス+遅延+ジッタが重なるとSRTのハンドシェイク
直後にメッセージの受信順序が乱れ、**受信側がクラッシュ(バッファオーバーフロー)
する不具合**が見つかった。対策として、メッセージ形式を以下に変更した。

```
[1byte 種別タグ] + [ペイロード]
  0x01 = CONFIG (ASC)  … 接続直後、以降は約100ms間隔で継続的に再送
  0x02 = AUDIO  (AACフレーム本体)
```

受信側はCONFIGを受信するまでAUDIOフレームを破棄し、CONFIG受信後に
デコーダを初期化する。これにより、接続直後の不安定な状況でも
自己修復するようになっている。

### 検証結果

| 条件 | latency_ms | 結果 |
|---|---:|---|
| ロスのみ 1〜3%(遅延なし) | 150〜300 | 完全回復(欠落なし) |
| ロス1%+遅延100ms/ジッタ20ms | 150 | 起動時のみ約85ms相当(4フレーム)欠落、以降は正常 |
| ロス1%+遅延100ms/ジッタ20ms | 300 | 完全回復(欠落なし) |
| ロス5%+遅延200ms/ジッタ50ms | 300 | 完全回復(欠落なし) |
| ロス5%+遅延200ms/ジッタ50ms | 500 | 完全回復(欠落なし) |

**結論:**
- ロスのみなら latency_ms を150ms程度に設定しても、SRTのARQでほぼ完全に回復する。
- 遅延・ジッタが絡む場合、CONFIG再送間隔(約100ms)により起動直後の欠落は
  最大でも100ms程度に収まる。一度デコーダが初期化されればその後の欠落はない。
- 実際の無線区間(W56系)は「瞬断」に近い挙動をするため、本検証の
  delay/jitterモデルより厳しい条件になる可能性がある。実機での追加検証を推奨。

### 自前で検証を再実行する場合

```bash
python3 test_matrix.py
```

`udp_lossy_proxy.py` と `test_matrix.py` は開発・検証用のツールであり、
本番のRaspberry Pi環境には配置不要(実機では `tc netem` を使用する)。
`tc netem` を使った試験手順は別途 `PACKET_LOSS_TEST.md` を参照。

## 長時間連続稼働・再接続処理(実施済み)

### メモリリーク確認
3分間(約8,400フレーム)の連続稼働でRSS(常駐メモリ)を5秒おきに記録。
起動直後の初期化分を除き、送受信ともRSSは完全に横ばいで、メモリリークは
見られなかった。

### 再接続処理
初期実装は接続が切れるとプロセスごと終了する仕様だったが、放送用途では
不適切なため、以下の自動再接続機能を追加した。

- **送信側**: 受信側との接続が切れてもプロセスは終了せず、標準入力(音声入力)
  が続く限り次の接続を待ち受け続ける。受信側が再接続すればCONFIGを送り直し、
  配信を再開する。
- **受信側**: 接続が切れると1秒間隔で自動的に再接続を試行し続ける
  (Ctrl+C/SIGTERMで明示的に終了するまで)。送信側が復帰すればCONFIGを
  受信してデコーダを再初期化する。

実際に片方を`SIGKILL`で強制終了させて検証し、両方向とも正常に再接続することを
確認済み。

### 送信側のパイプバッファ溢れ対策(修正済み)

当初「断線が数十秒以上続くとパイプバッファが埋まる」と見積もっていたが、
実測したところ誤りだった。Linuxのパイプバッファは既定64KB程度しかなく、
48kHz/16bit/stereoの音声ではわずか**約0.3秒分**にしかならない。実機の
`arecord`と組み合わせた場合、0.3秒の断線でも録音側がブロックし、ALSAの
録音バッファも溢れて音声データが失われる(overrun)可能性が高いことが
分かった。

**対策:** 音声読み取り(stdinの読み込み)を専用スレッドに分離し、ネット
ワークの接続状態と完全に切り離した。送信できない間(接続待ち・再接続待ち)
の音声フレームは「捨てる」設計にし、arecord側が絶対にブロックしないよう
にした。数十秒以上の長時間断線・電源断からの復旧は対象外(その間の音声は
失われる)としている。

**修正前後の実測比較:**

| 項目 | 修正前 | 修正後 |
|---|---|---|
| 10秒間の断線中に書き込めたバイト数 | 57,600(3%、即座にブロック) | 1,929,600(100.5%、ブロックなし) |
| 再接続後の配信速度 | 2.6倍速で早送りバースト | ほぼリアルタイム速度(早送りなし) |

### 累積稼働テスト(round_test.py)

上記のメモリリーク確認・再接続処理を、まとめて長時間(3分×10ラウンド=累積30分)
自動実行できるスクリプト。実際にビルド・実行して確認済み(全ラウンドで再接続
成功、メモリリークなし、30分後もFFTで音質劣化なしを確認)。

```bash
# 事前にこのディレクトリで make 済みであること(aac_srt_send/recvが生成済み)
python3 round_test.py
```

- 1回の実行で1ラウンド(3分強)だけ進む「再開可能」な作り。10ラウンド分
  行うには**このコマンドを10回実行する**(1回で30分通しにはしていない。
  長時間ブロックする処理が環境によって途中で打ち切られることがあるため、
  1ラウンドずつ確実に進める方式にしている)。
- 440Hz/660Hzのステレオテストトーンを自動生成し(`round_tone_5s.raw`、初回
  実行時のみ)、送信側に流し続ける。
- 各ラウンドの90秒目に受信側プロセスを`SIGKILL`で強制切断し、自動再接続を
  確認する。
- 出力: `round_rss.csv`(RSS推移)、`round_reconnect_events.txt`(再接続結果)、
  `round_send.log`/`round_recv.log`(プロセスログ)、`round_decoded.raw`
  (デコード済みPCM、末尾をFFTすれば音質確認可能)。
- 最初からやり直す場合は `round_state.txt round_rss.csv
  round_reconnect_events.txt round_send.log round_recv.log
  round_decoded.raw` を削除してから再実行する。

## 暗号化(有効化・パスフレーズ発行済み)

`aac_srt_send` / `aac_srt_recv` の最後にパスフレーズを渡すと、SRTのAES-128
暗号化が有効になる。

**本システム用に生成したパスフレーズ(24文字、英数字混在):**

```
m9I3S2y2OfPuVBN0uhjiMwBu
```

```bash
# 送信側
./aac_srt_send 9000 48000 2 96000 150 "m9I3S2y2OfPuVBN0uhjiMwBu"

# 受信側(同じパスフレーズ)
./aac_srt_recv <送信側IP> 9000 150 "m9I3S2y2OfPuVBN0uhjiMwBu"
```

パスフレーズは10〜79文字。省略時は従来通り平文で動作する。誤ったパスフレーズ
では`BADSECRET`エラーで明確に接続拒否されることを確認済み。

**注記:** ヤマハRTX等のVPN(IPsec)トンネル内でのみSRT通信を行う構成では、
既にVPN層で暗号化されているため、SRT側の暗号化は必須ではない。VPN区間外を
通る構成、または多層防御を意図する場合にのみ有効化を推奨する。

**パスフレーズの取り扱い注意:**
- このパスフレーズはREADME(平文)に記載されているため、ファイルの共有範囲には
  注意すること(社外に渡す資料に含めない等)
- 本番運用時は、このパスフレーズをそのまま使い続けるか、運用者が別途
  管理する文字列に差し替えるか、方針を決めておくとよい
- 送信側・受信側でパスフレーズが1文字でも異なると接続できない(`BADSECRET`)
